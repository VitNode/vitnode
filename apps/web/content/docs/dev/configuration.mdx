A VitNode app has **one** authored configuration file, `src/vitnode.config.ts`.
It describes the whole deployment - the site, the plugins, the API and the web
runtime - and it is **server- and build-only**. The browser never imports it.
Instead, your Vite build writes a browser-safe projection of it to
`src/vitnode.public.gen.ts`, and that generated file is what the document
shell, the router and every component read.

```ts title="src/vitnode.config.ts"
import { blogPlugin } from '@vitnode/blog/config'
import {
  defineApiRuntime,
  defineVitNodeConfig,
  defineWebRuntime,
} from '@vitnode/core/config'
import { coreRelations } from '@vitnode/core/database/relations'
import { SupabaseStorageAdapter } from '@vitnode/supabase-storage'
import { drizzle } from 'drizzle-orm/postgres-js'

import { appMessages } from './locales/app'
import { packageMessages } from './locales/packages'

export default defineVitNodeConfig({
  app: {
    i18n: {
      defaultLocale: 'en',
      locales: [
        { code: 'en', name: 'English' },
        { code: 'pl', name: 'Polski' },
      ],
      timeZone: 'UTC',
    },
    metadata: { shortTitle: 'VitNode', title: 'VitNode' },
  },

  plugins: [blogPlugin()],

  api: defineApiRuntime(({ env }) => ({
    dbProvider: drizzle({
      connection: env.POSTGRES_URL,
      relations: coreRelations,
    }),
    storage: {
      adapter: SupabaseStorageAdapter({
        url: env.SUPABASE_URL,
        secretKey: env.SUPABASE_SECRET_KEY,
        bucket: env.SUPABASE_STORAGE_BUCKET,
      }),
    },
  })),

  web: defineWebRuntime({
    public: {
      theme: { defaultTheme: 'system' },
    },
    server: () => ({ messages: appMessages, packageMessages }),
  }),
})
```

Four sections, and each one has a different reader:

| Section   | Holds                                                        | Read by                                             |
| :-------- | :----------------------------------------------------------- | :-------------------------------------------------- |
| `app`     | locales, time zone, site title                               | every runtime, and the public projection            |
| `plugins` | one factory call per installed plugin, with its options      | every runtime - each loads only the part it needs   |
| `api`     | a lazy factory for the database, storage, email, Redis, ...  | the Hono API only                                   |
| `web`     | browser-safe UI settings, and a lazy factory for the loaders | the public projection (`public`) and SSR (`server`) |

<Callout type="warn" title="Nothing runs when the config is evaluated">
  `defineApiRuntime` and `defineWebRuntime` take **functions**. Your Vite build
  loads `vitnode.config.ts` with `jiti` on every regeneration pass to find out
  which plugins are installed - so anything at the top level of that file runs
  during the build. Importing `drizzle-orm/postgres-js` or a storage adapter is
  free; *constructing* them is not. Keep every `drizzle(...)`, adapter call and
  environment read inside the factory, as above, and nothing connects to
  Postgres, opens Redis or starts cron until a runtime asks for it.
</Callout>

## One source, three projections

The authored file is never consumed directly. Each runtime asks for its own
projection, and each projection is an explicit allowlist rather than "the config
minus a few fields":

| Projection     | Built by                                      | Contains                                                                                               |
| :------------- | :-------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| **Public**     | your Vite build → `src/vitnode.public.gen.ts` | `debug`, `editor`, `theme`, locale metadata, site title, plugin ids and their sanitized public options |
| **Web server** | `createIntlMessagesLoader(config)`            | message loaders, package messages, the plugin list                                                     |
| **API**        | `resolveApiConfig(config)`                    | database provider, Redis, storage, email, AI, cron, SSO, captcha, rate limits, API plugin modules      |

### The public projection

```ts title="src/vitnode.public.gen.ts (generated)"
export const vitNodePublicConfig = {
  debug: false,
  i18n: { defaultLocale: 'en', localePrefix: 'as-needed', locales: [...], timeZone: 'UTC' },
  metadata: { shortTitle: 'VitNode', title: 'VitNode' },
  plugins: [{ pluginId: '@vitnode/blog', publicOptions: { postsPerPage: 20 } }],
  theme: { defaultTheme: 'system' },
} satisfies VitNodePublicConfig

export type VitNodeLocale = 'en' | 'pl'
```

This is the module browser code imports - the root route, `start.ts`, the
locale runtime, `pageHead`:

```ts title="src/lib/page-head.ts"
import { createRouteHead } from '@vitnode/core/tanstack/metadata'

import { vitNodePublicConfig } from '@/vitnode.public.gen'

export const pageHead = createRouteHead(vitNodePublicConfig.metadata)
```

`VitNodeLocale` is the literal union of your enabled locale codes, so
`Locale` stays `'en' | 'pl'` rather than `string`:

```ts title="src/lib/i18n/shared.ts"
import type { VitNodeLocale } from '@/vitnode.public.gen'

export type Locale = VitNodeLocale
```

<Callout type="info" title="Why a generated file">
  A generated module is ordinary TypeScript: your editor types it, Vite
  invalidates it, and a custom Vite frontend that is not TanStack Start reads it
  with a plain `import`. It regenerates on every `vite dev` and `vite build`
  whenever `vitnode.config.ts` changes, and it is committed like the other
  `src/*.gen.ts` files.
</Callout>

### The web server projection

SSR needs the message loaders, which read JSON out of package build output and
must never reach a browser. They live in `web.server`, and the loader resolves
them lazily on the first request:

```ts title="src/server/messages.server.ts"
import '@tanstack/react-start/server-only'
import { createIntlMessagesLoader } from '@vitnode/core/tanstack/i18n/server'

import vitNodeConfig from '@/vitnode.config'

export const loadIntlMessages = createIntlMessagesLoader(vitNodeConfig)
```

### The API projection

`resolveApiConfig` runs the `api` factory, then imports each plugin's API entry
and hands it that plugin's normalized options:

```ts title="src/server/vitnode-api.server.ts"
import '@tanstack/react-start/server-only'
import { OpenAPIHono } from '@hono/zod-openapi'
import { VitNodeAPI } from '@vitnode/core/api/config'
import { resolveApiConfig } from '@vitnode/core/config/server'

import vitNodeConfig from '@/vitnode.config'

const app = new OpenAPIHono().basePath('/api')

VitNodeAPI({ app, vitNodeApiConfig: await resolveApiConfig(vitNodeConfig) })
```

The factory receives a framework-neutral context - `{ env, mode }` - so a
config reads `env.POSTGRES_URL` rather than `process.env`, and a test can hand
it any environment it likes.

## Plugins are registered once

```ts
plugins: [blogPlugin(), examplePlugin()]
```

`blogPlugin()` returns a lightweight descriptor: the plugin id, the modules the
plugin provides, its normalized options and the subset it exposes publicly.
Calling it imports no React, no Hono, no database model - the descriptor is what
every runtime reads to decide what to load:

| Consumer          | Loads from the descriptor               |
| :---------------- | :-------------------------------------- |
| Hono API          | `entries.api`, with the options         |
| public router     | `entries.routes`                        |
| AdminCP sidebar   | `entries.adminNav`                      |
| Content Engine UI | `entries.adminContent`                  |
| public projection | the id and the sanitized public options |

A plugin that provides no API contributes nothing to the API, and one without
pages contributes nothing to the router - each consumer skips what is not there.
Pass options through the same call:

```ts
plugins: [blogPlugin({ postsPerPage: 12 })]
```

The plugin owns its option types, defaults, validation and what is public. See
[Plugin options](/docs/dev/plugins/options), and
[Create a plugin](/docs/dev/plugins/create) for the factory itself.

<Callout type="warn" title="There is no separate API registration">
  A plugin's API is loaded from the same factory registration. Nothing like
  `blogApiPlugin()` exists anymore - a plugin that provides an API advertises it
  through `entries.api`, and the API imports that entry at startup.
</Callout>

## Deployment modes

The same file describes every shape VitNode runs in. Leave out a runtime and
that side of the deployment does not exist.

<Tabs items={['Fullstack', 'API only', 'Web against a remote API']}>

```ts tab="Fullstack"
export default defineVitNodeConfig({
  app: { ... },
  plugins: [blogPlugin()],
  api: defineApiRuntime(async ({ env }) => ({ ... })),
  web: defineWebRuntime({ ... }),
})
```

```ts tab="API only"
export default defineVitNodeConfig({
  app: { ... },
  plugins: [blogPlugin()],
  api: defineApiRuntime(async ({ env }) => ({ ... })),
})
```

```ts tab="Web against a remote API"
export default defineVitNodeConfig({
  app: { ... },
  plugins: [blogPlugin()],
  web: defineWebRuntime({ ... }),
})
```

</Tabs>

- **API only** never imports TanStack Start. `apps/api` is this shape:
  `resolveApiConfig` plus `VitNodeAPI`, served by `@hono/node-server`.
- **Web against a remote API** configures no database and no API runtime. The
  universal `fetcher` talks to the API at `VITNODE_API_URL`. Asking such a
  config for an API projection is an error that names that variable.
- **A custom frontend** does not have to use VitNode routing or AdminCP at all.
  The API serves the same public projection at
  `GET /api/@vitnode/core/middleware` under `public`, so any client - a mobile
  app, another framework - reads the site's locales, title, plugin ids and
  public plugin options from one typed contract, `VitNodePublicConfig`.

## Why the browser cannot reach a secret

Two independent guards keep the root config out of the client bundle. Neither
relies on tree-shaking.

1. **Structural.** Browser code imports `src/vitnode.public.gen.ts`, a file
   your build writes from an explicit allowlist. The database provider, the
   storage secret key and every server-only plugin option are not fields it
   leaves out - they are fields it never copies.
2. **Enforced.** The `vitnode:client-guard` Vite plugin fails the client
   build when any chunk contains the root config, a plugin's `config.api`
   module, `drizzle-orm`, the Postgres or Redis drivers, a VitNode storage or
   email adapter - or the **value** of any secret-shaped environment variable
   (`*_SECRET*`, `*_PASSWORD*`, `*_API_KEY*`, `POSTGRES_URL`, `REDIS_URL`).
   In development the same guard refuses the import outright and names the
   file that made it.

This is also why a plugin's public options must be plain JSON: they are
written into the generated file, and a value that cannot be serialized - a
function, a `Date`, anything holding a secret by reference - is refused when
the factory is called.

## `start.ts` - the request pipeline

TanStack Start expects a `src/start.ts`, and it is part of the **client**
module graph - so it reads the public projection:

```ts title="src/start.ts"
import { createVitNodeStart } from '@vitnode/core/tanstack/start'

import { vitNodePublicConfig } from '@/vitnode.public.gen'

export const startInstance = createVitNodeStart({ config: vitNodePublicConfig })
```

`createVitNodeStart` installs three things, and none of them is optional:

| Middleware    | What it does                                                                              |
| :------------ | :---------------------------------------------------------------------------------------- |
| **CSRF**      | Rejects cross-site requests to server functions (`handlerType === 'serverFn'`)            |
| **Locale**    | Canonical `308` redirects, the remembered-locale cookie, and the document cache directive |
| **Documents** | Forces `Cache-Control: private, no-store` onto every HTML response                        |

Add your own with `requestMiddleware`; it runs after those three, in the order
you list it:

```ts title="src/start.ts"
export const startInstance = createVitNodeStart({
  config: vitNodePublicConfig,
  requestMiddleware: [requestId],
})
```

## `vite.config.ts`

One VitNode plugin, which composes the environment handling, the dev server's
dependency pre-bundling, the SSR externals, the projection generator and the
client guard in the order they have to run:

```ts title="vite.config.ts"
import { vitnode } from '@vitnode/core/framework/vite'

export default defineConfig({
  plugins: [
    vitnode({ appRoot: import.meta.dirname }),
    nitro(),
    tailwindcss(),
    tanstackStart(),
    viteReact(),
  ],
})
```

`appRoot` has to be `import.meta.dirname`: a Vite config is loaded with the
working directory set to wherever the command ran. The generator reads
`src/vitnode.config.ts` (or a root-level `vitnode.config.ts`) and writes four
files: `plugin-routes.gen.ts`, `admin-nav.gen.ts`, `content-registry.gen.ts`
and `vitnode.public.gen.ts`.

Publish an extra key to the browser with `clientEnv`, and widen the client
guard with `clientGuard.forbiddenModules` when your app has server-only modules
of its own:

```ts
vitnode({
  appRoot: import.meta.dirname,
  clientEnv: ['VITNODE_MAP_KEY'],
  clientGuard: { forbiddenModules: [/\/src\/secrets\//] },
})
```

## Migrating from the three config files

Earlier canary releases authored `vitnode.config.ts`,
`vitnode.server.config.ts` and `vitnode.api.config.ts`, and registered each
plugin twice. Those builders are gone: `buildConfig`, `buildServerConfig`,
`buildApiConfig`, `getVitNodeConfig` and the `*ApiPlugin()` factories no longer
exist, and a `vitnode.config.ts` that still exports `vitNodeConfig` fails the
build with a message naming this section.

<Tabs items={['Before', 'After']}>

```ts tab="Before"
// src/vitnode.config.ts
export const vitNodeConfig = buildConfig({
  i18n: { ... },
  metadata: { ... },
  plugins: [blogPlugin()],
  theme: { defaultTheme: 'system' },
})

// src/vitnode.server.config.ts
export const vitNodeServerConfig = buildServerConfig({
  config: vitNodeConfig,
  messages: appMessages,
  packageMessages,
})

// src/vitnode.api.config.ts
export default defineVitNodeConfig({
  // ...
  api: defineApiRuntime(async ({ env }) => ({
      plugins: [blogApiPlugin()],
      i18n: vitNodeConfig.i18n,
      metadata: { ... },
      dbProvider: drizzle({ connection: env.POSTGRES_URL }),
  })),
})
```

```ts tab="After"
// src/vitnode.config.ts
export default defineVitNodeConfig({
  app: { i18n: { ... }, metadata: { ... } },
  plugins: [blogPlugin()],
  api: defineApiRuntime(({ env }) => ({
    dbProvider: drizzle({ connection: env.POSTGRES_URL }),
  })),
  web: defineWebRuntime({
    public: { theme: { defaultTheme: 'system' } },
    server: () => ({ messages: appMessages, packageMessages }),
  }),
})
```

</Tabs>

Then, file by file:

| Was                                                                | Becomes                                                                        |
| :----------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| `import { vitNodeConfig } from '@/vitnode.config'` in browser code | `import { vitNodePublicConfig } from '@/vitnode.public.gen'`                   |
| `createVitNodeStart({ config: vitNodeConfig })`                    | `createVitNodeStart({ config: vitNodePublicConfig })`                          |
| `createIntlMessagesLoader(vitNodeServerConfig)`                    | `createIntlMessagesLoader(vitNodeConfig)` (the default export)                 |
| `VitNodeAPI({ app, vitNodeApiConfig })`                            | `VitNodeAPI({ app, vitNodeApiConfig: await resolveApiConfig(vitNodeConfig) })` |
| `defineVitNodeDrizzleConfig({ vitNodeApiConfig, dbCredentials })`  | `defineVitNodeDrizzleConfig({ config: vitNodeConfig, out })`                   |
| `plugins: [blogApiPlugin()]` in the API config                     | delete it - `blogPlugin()` in `plugins` already covers the API                 |
| `(typeof vitNodeConfig.i18n.locales)[number]['code']`              | `VitNodeLocale` from the generated file                                        |

Delete `vitnode.server.config.ts` and `vitnode.api.config.ts`. Plugin authors
replace `buildPlugin({ pluginId, messages, routes })` with
`definePluginFactory({ pluginId, entries })` and export `apiPlugin` from
`config.api.ts` instead of a `*ApiPlugin()` factory - see
[Plugin options](/docs/dev/plugins/options).
